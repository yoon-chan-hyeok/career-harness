## 어떤 서비스인가요?

지원할 때마다 공고를 다시 읽고, 예전에 한 일을 찾고, 문항마다 어떤 경험을 쓸지 정합니다. AI에 작성을 맡겨도 기술 키워드만 보고 직무를 연결하거나, 내 역할과 성과 수치를 바꾸는 일이 생깁니다.

**Career Harness는 이 반복 작업을 지원 한 건의 흐름으로 연결합니다.** 공고에서 실제 맡는 일을 정리하고, 현재 확인된 경험을 근거로 연결합니다. 어떤 메시지를 보여 줄지 정한 뒤 문항의 의도와 권장 구성을 확인하고 작성합니다. 자소서와 이력서, 검수 질문과 수정 이력을 별도로 보관해 다음 지원이나 면접 준비에 이어 갑니다.

취업 준비 중 경험과 문서가 여러 곳에 흩어져 있거나, 초안의 표현을 어디까지 믿어도 될지 확인하고 싶은 사람을 위한 서비스입니다.

| 지원 전략 | 보여 줄 강점과 문항별 경험을 선택하고 승인 | 지원 전략·문항별 메시지 |
| 초안 전 작성 설계 | 문항 의도·권장 배분·예시를 읽고 경험·강조 방향·메모를 선택 | 화면과 작성 입력에 연결된 문항별 설계 |
| 자소서·이력서 작성 | 확인한 근거로 작성하고 문서별로 수정 | 문항별 초안·구조화된 이력서·버전 |
| 검수·최종본 보관 | 수치·기여·출처·문항 답변을 확인하고 최종본을 잠금 | 검수 기록·보관본·면접 준비 자료 |

**최종본 보관과 실제 제출은 별도입니다.** 채용 사이트에 자동으로 지원서를 제출하지 않습니다.

## 지원 한 건의 흐름

~~~mermaid
flowchart LR
    A["경험·공고 등록"] --> B["직무 분석·근거 연결"]
    B --> C["전략 선택·사용자 승인"]
    C --> D["문항별 설계·주장 검증"]
    D --> E["메시지 승인·자소서 작성"]
    C --> R["이력서 구성·작성"]
    E --> F["검수·수정"]
    R --> F
    F --> G["최종 확인·보관"]
    G --> H["면접 준비"]
~~~

문항별 설계는 자소서 경로이고, 이력서는 같은 현재 사실과 근거를 사용하는 별도 구성·검수 경로입니다. 경험이나 전략이 바뀌면 연결된 문서의 재검토가 필요합니다. 이미 보관한 최종본은 당시 상태로 유지합니다.

<details>
<summary>승인과 근거 검증은 어떻게 연결되나요?</summary>

전략 승인 뒤 문항별 의도·권장 배분·예시·경험·메모를 준비합니다. 이어서 핵심 메시지와 주장을 설계하고, Evidence Test가 선택한 원자료로 주장을 검증합니다. 사용자가 메시지를 승인해야 초안으로 진행할 수 있습니다. 검수에서 질문이나 수정이 생기면 해당 문서를 고친 뒤 다시 확인합니다. AI가 사용자의 승인이나 실제 제출 완료 확인을 대신하지 않습니다.

</details>

## 반복하던 판단을 어떻게 도와주나요?

| 고민 | 서비스에서 적용한 판단 |
|---|---|
| “RAG를 써봤으니 이 직무도 맞을까?” | 키워드와 함께 실제 산출물·핵심 업무·직접 경험·부족한 역량을 봅니다. |
| “이 문항에 어떤 경험을 얼마나 쓸까?” | 문항 의도와 권장 구성을 먼저 보고, 보여 줄 판단과 본인 행동을 배분합니다. |
| “예시처럼 쓰면 내 성과도 그렇게 되는 걸까?” | 표현 참고와 사실을 분리합니다. 예시의 프로젝트·기관·수치를 내 경력으로 가져오지 않습니다. |
| “팀에서 한 일을 내가 다 했다고 써도 될까?” | 본인 기여와 주장에 현재 근거를 연결하고, 부족하면 질문하거나 범위를 좁힙니다. |
| “내 역할을 정정했는데 초안은 그대로일까?” | 연결된 결과를 재검토 상태로 바꾸고 근거·메시지를 다시 확인합니다. |

현재 원문 가이드는 특정 회사·직무·문항·글자 제한이 일치하는 1개입니다. 다른 문항은 7종 유형에 따른 **제안 구성**을 제공합니다. 예를 들어 600자 문항의 70/120/280/130자 배분은 등록된 가이드의 권장 예시이며 모든 문항의 고정 공식은 아닙니다.

## 내가 설계한 페이즈: 지원서를 완성하는 26단계

취업 준비를 하면서 같은 지시를 반복했습니다. “JD부터 봐”, “이건 내가 직접 한 일이 아니야”, “문항 전체의 역할부터 나눠”, “채용담당자 관점에서 다시 봐”. Career Harness에는 이때 필요했던 판단 순서와 확인 절차를 담았습니다. 글을 생성하는 순간보다, **어떤 근거로 무엇을 말할지 결정하는 과정**을 길게 설계한 이유입니다.

아래 1~26은 작성전략의 단계이며 화면 26개나 AI 호출 26회를 뜻하지 않습니다. 여러 단계가 하나의 작업 화면·저장 결과를 공유하고, 사실이나 전략을 고치면 앞 단계로 돌아갑니다. 문항별 14~25단계는 각 문항에서 반복하고, 마지막에는 지원서 전체를 함께 확인합니다. 레쥬메 경로와 개발 계획 M0~M14는 뒤에 따로 설명합니다.

**현재 범위:** 단계별 데이터·실행 경로·승인 조건을 연결하고 합성 자료로 검사했습니다. 공개 서비스의 실제 AI 생성 경로도 일부 확인했지만, 개인 전체 자료와 6종 규칙을 넣어 이 26단계를 모두 거친 최종 지원서 품질 검증은 아직 통과하지 못했습니다. 아래 설명은 각 단계의 목적과 구현 방식을 설명하며, 전 단계 품질 보증을 뜻하지 않습니다. [단계별 인수 점검표](docs/RULE_PACK_AND_RESUME_AUDIT_2026_10_13.md) · [실제 입력에서 확인한 한계](docs/REAL_INPUT_ACCEPTANCE_2026_10_15.md)

### A. 회사가 실제로 맡기려는 일 파악하기 · 1~7

#### 01. 최신 JD 확인

분석할 공고 원문과 출처, 마감일·시간대를 먼저 남깁니다. 예전에 저장한 공고를 현재 공고처럼 쓰거나 마감 기준을 놓치는 일을 줄이려는 단계입니다. 원문이 바뀌면 그 공고에 의존한 분석도 다시 확인합니다. 외부 채용 사이트의 최신성을 자동으로 모두 보장하는 기능은 아닙니다.

#### 02. 회사·사업·조직 조사

회사가 무엇을 팔고, 어느 조직이 어떤 문제를 다루는지 공고와 공개 자료에서 확인합니다. 사실마다 출처와 원문 인용을 붙이고, 자료가 부족하면 JD만으로 분석한다는 한계를 표시합니다. 무료 추론 모델과 자료 수집은 분리했으며, 현재 공개 수집은 공고의 최대 두 링크와 사용자가 추가한 자료를 사용합니다. 모든 사이트를 탐색하는 검색 엔진은 아닙니다.

#### 03. 과거·경력·유사 JD와 비교

현재 공고만으로 역할이 모호하면 과거 공고, 경력직 공고, 현직자 설명, 유사 직무 자료에서 추가 신호를 찾습니다. 과거 자료의 날짜와 적용 범위를 남겨 현재 조직의 확정 사실로 섞지 않습니다. 이 단계의 결과는 직무 해석의 보조 근거이며, 실제 탐색의 충분성은 별도 확인 대상입니다.

#### 04. Why Now: 지금 이 사람을 뽑는 이유

사업·조직 자료와 채용 내용을 연결해 채용 배경을 한 문장 가설로 정리합니다. 회사가 직접 밝힌 사실과 지원자가 추론한 이유를 나누고, 근거와 한계를 사용자가 확인합니다. 현재 사업 소개만 보고 과거 채용의 긴급성을 단정하는 식의 추론은 채택하지 않습니다.

#### 05. Actual Output: 입사 후 만들 산출물

“Python을 쓴다”에서 멈추지 않고, 그 기술로 어떤 분석·시스템·보고서·운영 결과를 만들어야 하는지 적습니다. 이후 경험 검색과 지원 전략은 이 산출물에 맞춥니다. 핵심 업무를 빠뜨리지 않는 것이 목적이므로 항목 수를 기계적으로 세 개에 고정하지 않습니다.

#### 06. 본업·전문 분야·도구 분리

본업인 Base Profession, 전문 분야인 Specialty, 업무에 사용하는 Tool을 나눕니다. 공고에 AI나 RAG가 등장한다는 이유만으로 직업 정체성을 AI 연구자·RAG 개발자로 정하지 않기 위해서입니다. 회사·직무 분석 결과는 이 단계까지 지원자 경험과 분리해 보관합니다.

#### 07. Main Skill과 Differentiator 구분

업무를 맡기기 위해 반드시 필요한 핵심 역량과, 그 위에서 차별점이 되는 역량을 나눕니다. 지원자의 눈에 띄는 프로젝트가 본업의 필수 역량을 대신하지 않게 하는 기준입니다. 이 구분은 자소서의 주력 메시지뿐 아니라 레쥬메 경험 순서에도 쓰입니다.

### B. 내 근거로 지원 전략 결정하기 · 8~13

#### 08. Direct / Adjacent / No Evidence 매핑

각 업무 산출물에 내 경험을 연결합니다. 직접 해 본 일은 Direct, 비슷한 판단이나 기술을 옮겨 쓸 수 있는 경험은 Adjacent, 증명할 자료가 없으면 No Evidence로 남깁니다. 기술 이름이 같다는 이유만으로 직접 경험으로 승격하지 않으며, 연결한 근거의 출처와 소유자도 확인합니다.

#### 09. Fatal Gap과 대응 판단

필수 자격 미충족이나 핵심 업무 경험 부족을 전략에 드러냅니다. 보완 가능한 공백과 지원 판단에 큰 영향을 주는 공백을 구분하고, 지원할지·어떤 한계를 인정할지 결정합니다. 글을 잘 다듬었다는 이유로 없던 역량이 생긴 것처럼 처리하지 않습니다.

#### 10. 현재 Fact 재확인

원자료, 실제 기여 범위, 수치의 조건과 최신 정정을 확인합니다. 관련 과거 교정·회고도 검토하되, 탈락 원인에 관한 추측은 확정 사실과 구별합니다. “이건 내가 한 일이 아님”, “이 수치가 틀림”이라는 정정은 저장된 근거를 바꾸고, 그 근거를 사용한 결과를 재검토 상태로 만듭니다.

#### 11. 맡길 일 한 문장

회사가 나를 채용하면 무엇을 맡길 수 있는지 한 문장으로 적습니다. 자기평가 형용사보다 실제 업무와 연결된 문장을 전략의 중심에 둡니다. 이 문장은 비워 둘 수 없고, 현재 근거와 공백을 포함한 지원 전략 안에서 승인합니다.

#### 12. Persona 도출

직무 해석과 근거 매핑을 마친 뒤, 이번 지원에서 어떤 사람으로 기억될지 정합니다. 모든 회사에 같은 “AI 인재” 정체성을 먼저 씌우지 않습니다. 본업, 주력 역량, 차별점이 서로 맞는지 검토하고 사용자가 전략을 승인한 다음 문항 설계로 넘어갑니다.

#### 13. 문항 전체의 역할 배분

여러 문항이 있으면 각 문항이 증명할 역량·메시지·경험을 먼저 나눕니다. 같은 프로젝트를 쓰더라도 다른 판단과 기여를 보여 주도록 하고, 같은 숫자나 결론의 반복을 점검합니다. 다문항 지원은 이 배분을 승인해야 개별 문항을 설계할 수 있습니다.

### C. 문항마다 초안 전에 설계하기 · 14~20

#### 14. 문항 의도 해석

질문의 표면적인 주제와 회사가 확인하려는 역량을 나눠 읽습니다. 지원동기·협업·도전처럼 유형이 달라지면 답해야 할 질문과 필요한 경험도 달라집니다. 초안 전 작성 설계 화면에서 문항 의도와 권장 구성을 먼저 보여 줍니다.

#### 15. 문항에 쓸 Fact 다시 확인

전체 경험 보관함에서 이번 문항에 사용할 경험과 보조 근거를 고릅니다. 선택한 원문, 수치, 직접 수행 범위와 하지 않은 일을 문항 설계에 전달합니다. 경험을 바꾸면 이전 메시지·초안·검수 결과도 다시 확인해야 하므로, 이미 승인한 주장에 새 근거를 조용히 끼워 넣지 않습니다.

#### 16. 과거 자소서와 승인 표현 검색

예전 글에서 도움이 되는 논리 순서와 말투를 찾습니다. 사실 저장소와 표현 저장소를 분리해 과거 회사명·수치·기여가 현재 사실을 덮지 않게 합니다. 잠근 글의 표현도 사용자가 범위를 정해 승인하며, 원문 문장 재사용에는 별도 허용과 현재 근거 검사가 필요합니다.

#### 17. Operational Value로 번역

기술적으로 한 일을 업무상 어떤 가치로 설명할지 정합니다. 예를 들어 평가·진단 절차를 만들었다면, 무엇을 판단하거나 확인하기 쉬워졌는지 현재 근거로 설명합니다. 측정하지 않은 매출·운영 효과를 성과 수치로 만들지 않고, 실험 결과와 실제 운영 효과의 범위를 구분합니다.

#### 18. Provisional Claim: 핵심 주장 후보

이번 문항에서 독자가 기억해야 할 핵심 메시지와 이를 받치는 주장을 제안합니다. 이때는 아직 확정 전입니다. 사용자가 경험·강조 방향·작성 메모를 조정할 수 있고, 주장마다 어떤 근거로 증명할지 연결합니다.

#### 19. Evidence Test → Claim Lock

주장이 근거로 뒷받침되는지, 더 강한 근거가 있는지, 면접에서 설명할 수 있는지 확인한 뒤 메시지를 승인합니다. 실패·미확인 결과가 남으면 잠금을 막습니다. 메시지를 승인한 뒤에도 근거가 바뀌면 다시 검토해야 하며, 문장 생성이 사실 승인이나 사용자 승인을 대신하지 않습니다.

#### 20. PODAEIJ로 서사와 분량 설계

Problem → Observation → Decision → Action → Evidence → Insight → Job Relevance 중 문항에 필요한 요소를 고릅니다. 무엇을 했는지 나열하는 데서 그치지 않고, 어떤 관찰로 왜 그 결정을 내렸는지를 드러내려는 구조입니다. 모든 요소를 일곱 문단으로 강제하지 않습니다.

이 구간에 **문항별 작성 설계 화면**을 연결했습니다. 문항 의도, 부분별 권장 글자 수, 참고 예시의 역할, 출처, 경험 선택, 부족한 정보와 메모를 읽고 조정한 뒤 작성합니다. 화면과 실제 작성 입력은 같은 가이드·버전을 사용합니다. 보관된 원문 가이드는 정확한 조건의 문항 1개이며, 다른 7종 구성은 제안으로 표시합니다. 예시 속 프로젝트와 수치는 사용자 사실로 가져오지 않습니다. [구현·공개 검증 기록](docs/WRITING_PLAN_2026_10_17.md)

### D. 작성·검수·수정·잠금 · 21~26

#### 21. 초안 생성

승인한 전략·메시지와 현재 근거, 작성 설계, 글자 제한을 전달해 초안을 만듭니다. 사용자가 보호한 문장은 수정 범위를 제한하고, 생성한 주장과 근거의 연결을 장부로 남깁니다. 입력 한도를 넘으면 사실이나 규칙을 몰래 잘라 진행하지 않고 실패 이유를 표시합니다.

#### 22. Fact / Ownership 검수

문장 속 주장·숫자·직접 기여를 원자료와 대조합니다. 팀 전체 결과를 개인 결과로 확장하거나 실험을 운영 성과로 바꾸는 표현, 프로젝트별 금지 주장을 검사합니다. 결정적 조건 검사와 모델 검수를 함께 사용하며, 모든 자연어 과장을 자동으로 발견한다고 보장하지는 않습니다.

#### 23. Reverse Test: 내 글을 내가 설명할 수 있는가

강한 주장이나 불명확한 기여에서 예상 질문을 만들고 답변·근거·처리 방법을 기록합니다. 문서를 고칠지, 근거를 보완할지, 면접에서 설명할지, 공백을 인정할지 결정합니다. 필수 답변이 남으면 최종 잠금을 막고, 사실 오류를 단순한 면접 준비 항목으로 넘기지 않습니다.

#### 24. Red Team: 채용담당자 관점으로 다시 읽기

질문에 직접 답하는지, 본업이 먼저 보이는지, 기술 설명이 핵심 메시지를 가리지 않는지 검토합니다. 여러 문항과 레쥬메 사이의 사실·기여 충돌과 반복도 함께 확인합니다. 마지막에는 사용자가 맡길 일, 본업을 원하는 이유, 경험이 그 역량의 증거가 되는 이유를 직접 답하고 남은 공백을 확인합니다.

#### 25. 압축과 필요한 부분 수정

검수에서 나온 문제를 기준으로 수정안을 제안하고, 사용자가 승인한 뒤 새 버전에 반영합니다. 글자 수만 줄이면서 핵심 판단과 근거가 사라지지 않게 확인합니다. 수정 후에는 이전 검수를 그대로 인정하지 않고 다시 검사하며, 자동 수정은 무제한 반복하지 않습니다.

#### 26. Lock: 현재 최종본 확정

최신 본문·근거·검수·필수 답변·문서 전체 확인이 맞는 버전을 잠급니다. 이후 변경이 생기면 관련 확인을 다시 받아야 하며, 이미 만든 제출 보관본은 덮어쓰지 않습니다. **문항 잠금, 지원서 최종본 보관, 실제 제출은 각각 다른 상태**입니다. 실제 제출 상태는 사용자가 명시적으로 확인해야 바뀝니다.

### 레쥬메·면접·회고는 어디에 연결되는가

레쥬메는 공고 분석·근거·지원 전략을 공유하면서 별도 작성 경로로 진행합니다. 마스터 레쥬메에서 경험을 재사용하고, Main Skill에 맞춰 프로젝트 순서와 bullet을 구성한 뒤 사실·가독성·분량을 검수합니다. 1페이지·2페이지·마스터의 내용 예산을 구분하며, 내보낸 파일의 실제 페이지 수와 레이아웃은 별도 확인 대상입니다. 자소서와 함께 지원할 때에는 두 문서 사이의 사실과 수행 범위도 맞춥니다. [레쥬메 설계](docs/09_RESUME_IMPLEMENTATION_SPEC.md) · [분량·규칙 연결 보완](docs/RULE_PACK_AND_RESUME_AUDIT_2026_10_13.md)

지원서 최종본을 보관하면 당시 근거와 검수 답변을 담은 불변 스냅샷을 만들고, 면접 준비 자료는 그 제출본을 기준으로 이어집니다. 이후 합격·탈락·교정 기록을 남길 수 있지만, 코딩테스트 탈락을 자소서 실패로 단정하거나 새 규칙을 자동 승격하지 않습니다. [상태 전이와 보관 원칙](docs/05A_STATE_MACHINE_SPEC.md)

### 최초 계획 이후 실제 사용 요구로 보완한 페이즈

원래 계획에 있던 이름만 채우는 것으로는 충분하지 않았습니다. 첨부 작성전략과 실제 사용 요구를 대조하면서 아래 흐름을 추가로 보완했습니다.

1. **6종 작성 규칙을 실행 단계에 연결.** 자소서 전략, Resume 규칙, 공고 우선순위, 공통 사실성, 운영가치 표현집, RULE_REGISTRY를 단계별로 전달합니다. 초기의 고정 요약 누락을 찾아 원문 절·버전·적용 단계 기준으로 보완했고, 예시와 과거 스냅샷은 현재 경력 사실과 분리했습니다. [규칙 연결 감사](docs/RULE_PACK_AND_RESUME_AUDIT_2026_10_13.md)
2. **검수 결과를 실제 후속 작업에 연결.** 질문을 보여 주는 데서 끝나지 않고 답변·인용·수정 승인·재검수·최종 확인으로 이어지게 했습니다. 기여 경계와 문항 간 반복도 최종 보관 조건에 반영했습니다. [검수 대응](docs/REVIEW_RESPONSE_PROGRESS_2026_10_07.md) · [최종 직접 확인](docs/FINAL_REVIEW_PROGRESS_2026_10_10.md) · [문서 간 일관성](docs/DOCUMENT_CONSISTENCY_2026_10_13.md)
3. **실제 AI와 공개 체험 연결.** 로컬·합성 검사에서 외부 HTTPS·DB·무료 AI 경로로 넓혔습니다. 방문자별 자료 격리, 저장·내보내기·본인 삭제를 확인했고, 인증메일은 사용자 결정에 따라 뒤로 미뤘습니다. [공개 체험 검증](docs/GUEST_TRIAL_2026_10_14.md)
4. **개인 지원서 재현 검증과 입력 한도 확인.** 승인된 개인 자료로 실제 호출을 시작했지만, 큰 규칙·스키마 입력이 무료 한도를 넘는 단계에서 막혔습니다. 회사 자료 추출 성공을 전체 자소서 완성으로 표시하지 않았습니다. 다음 과제는 필수 근거와 규칙을 보존하는 단계별 입력 설계입니다. [실제 입력 기록](docs/REAL_INPUT_ACCEPTANCE_2026_10_15.md)
5. **초안 전 이해 화면 추가.** 사용자가 문항 의도·배분·예시·선택 경험을 이해하고 조정한 뒤 쓰도록 중간 단계를 넣었습니다. 화면에서 고른 구성이 실제 문항 설계와 작성 입력에도 동일하게 전달되게 했습니다. [문항별 작성 설계](docs/WRITING_PLAN_2026_10_17.md)
6. **서비스를 설명하는 공개 자료 정리.** 홈페이지·실제 작업실·화면·흐름도·사례 영상을 연결해 처음 보는 사람도 서비스의 용도와 검증 범위를 이해하게 했습니다. 영상의 재구성 사례와 합성 화면을 실제 개인 지원서 결과와 구별했습니다. [공개 소개 검증](docs/README_SERVICE_REVIEW_2026_10_20.md)

다음 우선순위는 **단계별 입력 한도 해결 → 개인 자료로 전체 지원서 작성·비교 검증 → 운영 DB 복구 확인**입니다. 원문 가이드 확대와 개별 요청 속도 측정도 남아 있습니다. 인증메일은 보류, Jev는 선택 기능 미연결 상태이며, 사용자가 제외한 비교 실험은 완료해야 할 출시 조건에 다시 넣지 않았습니다.
