# 운영 계정 연결 진행 — 2026-10-12

실제 Supabase DB와 Vercel 프로젝트를 준비했다. 실제 AI 호출, 운영 앱 배포와 공개 회원가입은 아직 완료하지 않았다. 10월 11일의 프로젝트 없음 기록은 당시 연결에서의 확인이며 아래 결과로 갱신한다.

## 완료한 작업

- 사용자가 만든 `career-harness` Supabase 프로젝트가 Seoul 지역에서 정상 상태임을 확인했다. 사용자가 지정한 조직의 Free 플랜을 확인했다.
- 개인자료가 없는 합성 PostgreSQL에 기존 Alembic 전체 이력을 적용하고 스키마 일치를 확인했다. 스키마만 추출해 별도 빈 DB에 복원하고 다시 검사했다. 실제 Supabase의 public 테이블이 비어 있음을 재확인한 뒤 설치했다. 개인 DB와 개인 문서 행은 업로드하지 않았다.
- 서비스 테이블 41개에 RLS를 적용하고 PUBLIC·anon·authenticated 권한을 회수했다. 실제 DB에서 브라우저 역할에 접근 권한이 있는 테이블은 0개다. pgvector는 `extensions`에 설치했다.
- 실제 Supabase 검사에서 발견한 외래키 인덱스 누락 3건을 수정했다. 모델과 Alembic `0014`에 반영하고, 원본 합성 DB와 복원 DB 양쪽에서 적용 → 되돌리기 → 재적용 → 스키마 일치를 확인했다. 실제 Supabase에서도 head `0014`와 인덱스 3개를 확인했다.
- 로컬 개인 DB는 비공개 백업과 무결성을 확인한 뒤 `0014`로 갱신했다. 기존 테이블별 행 수와 DB 무결성을 확인했다.
- 로그인한 Vercel 계정의 해당 팀 OWNER 권한과 활성 Hobby 플랜을 확인했다. `career-harness-api`와 `career-harness-web` 프로젝트를 만들고 공식 CLI로 각각 로컬 연결을 완료했다. 프런트 Root Directory는 `frontend`다.
- 백엔드 기본 설정 30개와 프런트 서버의 `BACKEND_URL` 1개를 Production 설정에 저장했다. 초기 상태는 회원가입 닫힘, 초대 모드, AI 제공자 `none`이다. DB 비밀번호·Supabase secret key·AI key는 아직 등록하지 않았다.
- 유료 플랜·유료 체험·크레딧 구매를 진행하지 않았다.

## 보안·성능 검사 결과

Supabase의 ERROR/WARN 보안 지적은 없다. [RLS 정책 없음 안내](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy) INFO 41건은 이 서비스가 브라우저의 테이블 직접 접근을 허용하지 않는 설계와 일치한다. 백엔드가 사용자 소유권을 검사하며 DB에 접속한다. 이 안내를 없애려고 브라우저 허용 정책을 추가하지 않았다.

외래키 인덱스 누락은 재검사에서 사라졌다. [미사용 인덱스 안내](https://supabase.com/docs/guides/database/database-linter?lint=0005_unused_index) INFO 102건은 새 빈 DB의 사용 이력이 없다는 뜻이며, 실제 운영 이력 없이 인덱스를 삭제하지 않았다.

## 로컬 검증

전체 Python 642개 통과, PostgreSQL 기능 검사 6개는 이 실행에서 생략했다. PostgreSQL 스키마 변경은 별도 실제 합성 DB 두 개에서 적용·되돌리기·재적용·Alembic check를 통과했다. Ruff·Pyright·프런트 검사 26개·lint·typecheck·production build를 통과했다. 처음 제한 실행에서 발생한 임시 폴더 접근 오류와 비동기 검사 정지는 실행 환경을 수정한 뒤 정상 권한의 저장소 검증 절차로 재실행했다. 제품 인증이나 TLS를 완화하지 않았다.

꺼져 있던 로컬 앱을 기존 비공개 로그인으로 다시 실행했다. 검증 대상은 작업실 화면 → 같은 주소의 API 프록시 → 기존 로컬 DB → 응답이다.

| 확인 대상 | 결과 | 증거 |
|---|---|---|
| 작업실 화면 | 통과 | `/workspace` HTTP 200, 실제 로그인 화면, 브라우저 경고·오류 0개 |
| API 준비 상태 | 통과 | `/health`·`/ready` HTTP 200 |
| 프런트 프록시와 API 인증 | 통과 | 기존 소유자 로그인 성공, 잘못된 토큰 거부 |
| 기존 자료 읽기 | 통과 | 백엔드·프런트 프록시의 자료 목록 응답 성공 |
| AI 운영 | 미연결 | 실제 로컬 `none`, configured=false, live_verified=false |

이번 브라우저 확인은 로그인 화면까지이며, 로그인 후 전체 작성 흐름을 다시 수행한 결과는 아니다. 운영 Supabase에 앱 런타임이 접속한 결과도 아니다. 합성 검사용 Docker 컨테이너 두 개는 각각 ID·라벨·마운트를 확인하고 정리했다.

## 다음 연결에 필요한 사용자 입력

`work/production-private.json`은 로컬에서만 사용하는 입력 파일이며 Git과 배포에서 제외된다. Supabase Connect의 Session pooler URI·DB 비밀번호, 백엔드 전용 secret key, 내려받은 DB 공개 CA 인증서 경로를 입력한다. Groq 키가 없으면 그 항목은 비워 둘 수 있다. Groq Free 확인 항목은 실제 계정 조건을 확인한 경우에만 true로 바꾼다. 비밀값은 대화로 보내지 않는다.

Codex 편집창 자동 열기 결과는 `queued`였다. 사용자가 실제 화면에서 파일을 볼 수 있다는 증거가 없으므로 “열려 있다”고 안내하지 않는다. 현재 대화의 절대 경로 파일 링크로 직접 열 수 있도록 안내했다.

입력 후에는 DB TLS와 계정 연결을 확인하고, 비밀 설정을 서버에 등록한 뒤 검증한 프로젝트에 배포한다. 프로젝트 도메인은 아직 실제 운영 페이지로 검증하지 않았으며 서비스 URL로 소개하지 않는다.

## 출시 전 남은 범위

- 실제 DB 접속값, CA와 Supabase secret key 연결, 실제 무료 AI 호출과 문서 작성 검증.
- 실제 SMTP 발신 소유권, OTP 템플릿·수신, Turnstile, 운영자 이름·문의 이메일·보관 기간 설정. 확인 전 운영자 확인 플래그를 설정하지 않는다.
- 실제 HTTPS 앱 배포, 두 계정의 자료 격리·가입·동의·로그인·작성·저장·내보내기·탈퇴·오류 복구 확인.
- 운영 DB 백업 복원과 삭제 요청 재적용, 오류·용량 알림 확인.
- 작성전략의 프로젝트별 표현 경계, 문서 간 사실·수치·유사 표현 반복 검사와 전체 인수 확인.

공개 GitHub와 기존 소개 사이트는 유지한다. 소개 사이트의 가상 데모를 실제 AI/회원가입 운영 성공으로 취급하지 않는다. 사용자에게 제외 요청을 받은 비교·개선 실험은 출시 조건에 추가하지 않는다.
