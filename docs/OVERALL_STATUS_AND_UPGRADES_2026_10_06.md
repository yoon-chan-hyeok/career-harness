**주요 제품 기능과 공개 가입형 코드는 구현되어 있다. 실제 AI가 연결된 공개 운영 서비스는 아직 완성되지 않았다.** 계정 설정만 남았다고 표현하기에도 이르다. 배포 재현성, 운영 복구·알림, 실제 환경의 전 과정 확인과 일부 추가 개발이 남아 있다.

이번 작업은 현황 정리와 개선안 작성이다. 전체 테스트나 Astra 전체 코드 감사를 새로 수행하지 않았으며, 추가 기능 구현·외부 배포·유료 가입도 수행하지 않았다. 과거 테스트 결과와 이번 실행 확인을 아래에서 구별한다.

## 3. 이번에 직접 확인한 실행·소스 상태

- 로컬 화면과 주요 API 8개 모두 HTTP 200.
- backend health/ready 정상. 기존 소유자 인증 성공, 미인증·합성 토큰 거부.
- 개인 SQLite 무결성 정상, 마이그레이션 0013.
- AI 상태: **provider=none, manual_only, live_verified=false**.
- 현재 개인 환경은 local 인증이며 공개 가입형으로 전환하지 않았다.
- 현재 저장소 기준 커밋: 906fb1e. 이번 보고서 작성 전 **추적 파일 변경 50개 + 새 파일 44개**가 미커밋 상태였다.
- 이 프로젝트에 Git 원격 저장소가 설정되어 있지 않다. 로컬 파일은 있으나 최신 변경이 원격에 보관되고 배포된 상태는 아니다.
- 프런트엔드 의존성 잠금 파일은 있다. Python은 버전 범위만 지정되어 있고 잠금 파일은 없다.

전체 진행률을 하나의 백분율로 표시하지 않는다. 기존 체크포인트의 M0·M4·M8·M13·M14는 운영 배포·DB·실제 생성·Word 렌더·선택적 Jev 등의 확인을 남겨 두고 있다. 일부 오래된 기록의 Docker/PG 미검증 표현은 최신 격리 환경 통과 기록으로 대체되었지만, 실제 운영 Supabase 미검증은 여전히 유효하다.

## 5. 에이전트·MCP·RAG·Jev의 정확한 상태

### 에이전트

기업·공고 조사, 직무 분석, 경험·근거 연결, 지원 전략, 문항·이력서 작성, 근거·채용 관점 검수의 **6개 역할 묶음**을 표시한다. 내부에는 역할별 프롬프트와 일부 병렬 검토가 있고, 중앙 워크플로가 상태·승인·저장을 관리한다. 화면은 실제 실행·문서·호출 기록에 근거한다.

별도 자율 에이전트 6개가 항상 떠서 자유롭게 토론하는 구조는 아니다. 원래 설계의 역할 분리 요구를 충족하는 데 별도 서버나 자율 에이전트 군집이 필수는 아니다. 지금은 실제 모델 응답과 오류 복구를 확인하는 편이 더 우선이다.

### MCP

로컬 stdio 방식의 읽기 도구 3개가 있다: 프로필 조회, 검증된 경험 검색, 최종 제출 보관본 조회. 웹 서비스의 중심은 API와 워크플로다. **작성·수정·승인까지 전부 MCP로 구현되어 있거나 ChatGPT 프로젝트에 원격 연결된 상태는 아니다.** 원격 MCP 확장은 별도 후속 범위로 판단한다.

### RAG

근거를 검색해서 작성 문맥에 넣는 구조는 있다. 무료 HF/Groq 흐름의 기본 검색은 단어·문자열 기반이며, 기기에서 E5 모델을 사용하는 선택적 의미 검색도 구현되어 있다. 약 118MB의 모델 가중치 다운로드가 필요하다. 모든 대화가 자동으로 의미 검색을 사용하는 것은 아니다.

추가 개선은 기존 의미 검색과 작성 흐름 연결, 관련 근거 설명, 첫 모델 다운로드·실패 안내다. “RAG가 없음”이나 “전 기능 벡터 검색 완료” 모두 현재 상태를 정확히 표현하지 못한다.

### Jev 및 AI 절감 수치

Jev는 선택적 보조 판단 어댑터가 있으나 실제 호출은 미검증이다. 기본 출시에 필수로 켜지 않는다. 캐시·사용량 기록 구조가 있어도 실제 모델 호출이 없는 현재 상태에서 비용 절감률이나 품질 향상을 입증했다고 말할 수 없다.

## 6. 무료 운영에 관해 꼭 보고할 사실

1. Hugging Face 계정 보유와 앱의 추론 API 연결은 별개다. 공식 문서상 무료 계정의 추론 크레딧은 **월 $0.10이며 변경 가능**하다. 이 규모를 공개 서비스의 지속 운영 예산으로 삼기는 어렵다는 판단이다. [HF 공식 요금 안내](https://huggingface.co/docs/inference-providers/pricing)
2. Groq도 무제한이 아니다. 요청·토큰 제한이 조직 단위로 공유되므로 운영자 키 하나에 사용자들이 같은 제공자 한도를 소비한다. 실제 계정의 한도를 확인하고 기존 개인/전체 상한을 맞춰야 한다. [Groq 공식 제한](https://console.groq.com/docs/rate-limits)
3. Supabase 기본 메일 발송기는 운영용이 아니고 수신자 제한이 있다. 일반 사용자에게 OTP를 보내려면 실제 SMTP 구성이 필요하다. 가입 화면이 완성되었다는 것만으로 누구나 가입할 수 있는 서비스가 되지는 않는다. [Supabase 공식 SMTP 안내](https://supabase.com/docs/guides/auth/auth-smtp)
4. Vercel Hobby는 개인·비상업적 용도로 제한된다. 개인 포트폴리오와 향후 운영 목적, 사용량을 확인해야 한다. 공개 가입 자체를 곧바로 유료 플랜 필요 조건이라고 단정하지는 않는다. [Vercel 공식 Hobby 안내](https://vercel.com/docs/plans/hobby)

권장 방식은 실제 사용할 무료 제공자 한 곳을 먼저 검증하고, 전체 한도 소진 시 작성 요청을 명확히 중단하는 것이다. 유료 플랜 가입·크레딧 구매·자동 유료 전환은 현재 사용자 범위에 없다. “무료 서비스”와 “사용자가 늘어도 항상 0원으로 정상 제공”은 같은 약속이 아니다.

## 7. 출시를 막는 작업과 완료 기준

| 순서 | 작업 | 완료 판단 |

| 6 | 배포 환경 최종 동선 확인 | 실제 브라우저 다운로드, Word/PDF 결과, 모바일·키보드 조작, 인증 만료와 장애 복구 확인 |

계정 삭제 시 현재 자료와 벡터를 제거해도 최소 사용량·차단·삭제 기록과 기존 백업은 별도로 남는다. **백업 보관 일수 설정만으로 오래된 백업을 자동 삭제하지 않는다.** 운영 정책과 실제 작업을 연결해야 한다.

가입 중단 설정은 앱의 새 회원 승인을 막는다. 인증 공급자 쪽의 계정 생성도 멈추려면 Supabase 설정을 함께 바꿔야 한다. 긴급 AI 한도를 0으로 해도 이미 시작된 요청이 즉시 취소되는 것은 아니다.

배포 설정의 SMTP/CAPTCHA 확인 표시는 운영자의 확인 기록이지 원격 설정을 자동 검증한 결과가 아니다. 실제 확인 없이 통과 값으로 바꾸면 안 된다. 상세 절차: [공개 서비스 설정](PUBLIC_SERVICE_SETUP.md).

현재 상한이 있어 무한대로 저장되는 모든 경우를 방치한 구조는 아니다. 다만 공개 사용자가 늘었을 때 긴 이력 조회와 운영 데이터를 안정적으로 다루는 추가 작업은 필요하다. 위 목록은 확인된 오류만 나열한 취약점 보고서가 아니라 코드 근거에 따른 개선 우선순위다.

### 사용량이 늘거나 실제 지연이 확인될 때

- **오래 걸리는 작업의 대기열**: 현재 요청에는 약 100초 공통 제한과 실행 기록·중단 복구가 있다. 서버 재시작 후에도 계속되는 작업 대기열은 아니다. 실제 작성이 제한을 자주 넘거나 동시 요청이 증가하면 영속 대기열·재시도·취소·제공자별 처리량 제어를 도입한다.
- **첨부 저장소 분리**: 업로드 수·용량은 제한되어 있다. 자료 증가가 확인되면 첨부를 별도 저장소로 옮기고 다운로드·삭제·백업 범위를 연결한다.
- **의미 검색 연계**: 이미 있는 기기 E5 기능을 필요한 작성 단계에 선택적으로 연결한다. 첫 다운로드·기기 성능·실패 시 기본 검색을 고려한다.

현재 검사만으로 동시 사용자 100명·1,000명 지원을 주장하지 않는다. 예상 사용량을 정하고 실제 제공자 한도와 배포 환경에서 확인해야 한다. 이는 제외한 모델 비교 실험과 다른 기능·운영 확인이다.

## 9. UI·포트폴리오 후속안

현재 색감과 대화/오른쪽 문서 구조를 유지한다. 우선은 빈 화면의 다음 행동, 저장·최신본·재검토 상태 구분, 긴 목록, 오류 뒤 돌아갈 위치, 모바일·키보드 사용성을 다듬는다. 새 장식을 늘리는 작업은 실제 작동 확인보다 뒤에 둔다.

공개 포트폴리오는 사용자의 “나중에” 결정을 유지하며 다음 순서로 구성하는 것이 적절하다.

1. 개인 자료가 없는 합성 예제로 주요 흐름을 보여 주는 읽기 전용 데모.
2. 문제와 설계 의도: 왜 사실/표현을 나누고 승인·최종 보관을 분리했는지.
3. 구조도: Next.js → FastAPI 워크플로 → DB/검색 → AI 제공자, MCP는 별도 접근 어댑터임을 표시.
4. 근거 변경·허위 기여·중복 실행·무료 한도 소진에 어떻게 대응하는지 실제 동작 사례.
5. RAG와 Jev의 실제 사용 범위, 구현/합성 검사/실호출 확인을 구별한 설명.
6. 공개 첫 화면의 서비스명·아이콘·공유 미리보기와 검색 노출 설정. 개인 작업실 내용은 공개 홍보에 사용하지 않음.

포트폴리오의 설득력은 에이전트 수보다 근거 추적, 상태 관리, 오류 수정과 재현 가능한 배포에서 나온다는 판단이다. 비교 실험·성능 향상 수치 제작은 다시 범위에 넣지 않는다.

## 10. 사용자에게 필요한 정보

지금 보고 요청에 대한 답변을 막는 질문은 아니다. 실제 운영 연결 단계에서 다음 정보가 필요하다.

- 최종 서비스명, 표시할 운영자명, 문의 이메일, 백업 보관 기간.
- 사용할 Supabase/Vercel 프로젝트와 소스 저장소의 정확한 대상.
- 무료 AI 제공자 계정의 추론 키 및 실제 제공 한도, 운영 OTP를 발송할 SMTP와 도메인.
- 개인 비상업 포트폴리오 서비스로 운영할지, 향후 상업 운영까지 계획하는지.

비밀 키는 채팅·공개 문서가 아닌 앱의 연결 설정 또는 해당 서버 환경 설정에 입력한다. 기존에 정한 공개형 추가, 운영자 공용 AI, 무료 우선·유료 전환 금지, 비교 실험 제외는 그대로 유지한다.

## 11. 다음 작업 순서

**배포 재현성·데이터 조회 보강 → 실제 무료 AI 한 흐름 → 실제 인증·메일·DB → HTTPS 배포 → 복구·다운로드·접근성 최종 확인 → 포트폴리오 설명** 순서가 적절하다. 외부 계정이 필요 없는 코드 보강과 실제 계정 연결은 병행할 수 있다.

앞으로 “완료” 보고는 무엇의 완료인지 명시한다: 구현 완료, 로컬 검사 완료, 실제 서비스 연결 완료, 공개 운영 확인 완료. 현재는 첫 두 단계에 주로 해당하며 뒤 두 단계는 남아 있다.
