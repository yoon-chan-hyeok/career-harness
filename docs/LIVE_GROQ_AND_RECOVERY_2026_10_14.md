# 실제 Groq 연결과 작성 흐름 검증 — 2026-10-14

로컬 작업실에서 실제 Groq `openai/gpt-oss-120b` 호출, 자소서·레쥬메 생성과 저장, 한국어 PDF 미리보기를 확인했다. 발견한 재작성 경로와 분량 유지 오류를 수정했다. 공개 서비스 배포·회원가입 운영 완료는 아니다.

## 실제로 확인한 결과

- 사용자가 Groq 결제수단 등록이나 Developer 업그레이드 없이 가입·키 생성만 했다고 확인했다. 이 확인에 따라 무료 운영 확인 항목을 적용했다. 유료 플랜 가입, 유료 제공자 전환이나 크레딧 구매는 수행하지 않았다.
- 기존 로컬 소유자 인증으로 제공자를 설정하고 실제 합성 응답을 받았다. 재시작 후 백엔드와 화면의 API 프록시 모두 `groq`, `configured=true`, `live_verified=true`를 유지했다. 기존 자료 목록 조회와 잘못된 토큰 거부도 확인했다.
- 개인 자료를 포함하지 않는 별도 작업실에서 브라우저 → API → 실제 Groq → 저장된 버전 → 한국어 PDF를 확인했다. 실제 호출은 작성 2회, 검수 역할 3회, 레쥬메 작성 2회다. 이 중 첫 레쥬메 응답은 검증에서 거부됐으며 저장 성공으로 세지 않는다.
- 첫 자소서의 자료에 없는 팀 공유·안정성 효과를 검수가 지적했고 최종 잠금은 HTTP 409로 차단됐다. 프롬프트 보완 후 재작성한 자소서에는 이 표현이 없었다. 새 결과의 최종 승인·제출을 완료한 것은 아니다.
- 첫 레쥬메 응답은 표시 문장과 claim 원문이 달라 저장되지 않았다. claim에 표시 문장의 정확한 부분을 복사하고 상위 bullet에도 동일 근거 ID를 넣도록 프롬프트·스키마 설명을 보완했다. 재호출은 검증과 저장을 통과했고 PDF에서 한국어를 확인했다. 사실 검증 조건을 완화하지 않았다.
- 레쥬메의 기존 2페이지 설정을 유지했다. 합성 자료가 한 항목이므로 실제 PDF는 1페이지다. 2페이지를 채우거나 실제 취업 문서 품질을 보장한 결과가 아니다.

## 코드 수정과 기능 인수

- 분량을 새로 지정하지 않는 재작성은 기존 `1` / `2` / `MASTER` 설정을 유지한다. 최초 작성의 기본값은 1페이지다.
- 최신 문서가 근거 정정 때문에 STALE이 됐어도 현재 전략·문항 승인을 다시 거친 다음 `ㄱㄱ`로 새 버전을 작성할 수 있다. 이미 교체된 버전 선택은 계속 거부한다. 근거 검사와 직접 승인 조건도 유지한다.
- 자료가 적을 때 분량을 억지로 채우거나 문서화한 사실을 팀 공유·측정 성과로 확대하지 않도록 writer 지침을 보완했다. 공통 프롬프트 버전은 `2.0.1`이다.
- 혼합 직무·기술 직무의 HTTP 여정 2개와 복구 경계 4개를 추가했다. 공고 분석, 조사와 Why Now 확인, 전략·문항·근거 승인, 자소서 2문항·레쥬메, 정정 후 재작성, 압축 제안의 직접 수락, 검수 답변, 마지막 세 질문, 문서 간 검수, 보관과 명시적 제출 확인, 타 계정 접근 거부를 검사한다.
- 여정 검사에는 합성 원문 6종과 고정 응답을 사용한다. 실제 사용자 원문 6종 전체의 의미적 수용 여부나 모든 AI 단계의 품질을 증명하지 않는다. 전체 26단계의 실제 지원 건 인수는 계속 남는다.

## 운영 연결 상태

- 실제 Supabase Session·Transaction pooler 접속에 성공했다. 클라이언트 연결은 TLS와 `verify-full`을 사용한다. 관리형 pooler 뒤의 DB 연결 상태는 별도 항목이며 클라이언트 인증서 검증 결과와 혼동하지 않는다.
- 실제 DB는 Alembic `0014`, 테이블 41개, RLS 41개, 브라우저 역할의 테이블 접근 권한 0개다. Supabase secret key·publishable key와 공개 서명키 조회도 성공했다.
- 배포 설정을 로컬 메모리에 적용한 읽기 전용 preflight에서 설정·DB·migration·검색·Data API 보호·Supabase 서명키를 통과했다. 이 검사는 클라우드 함수 실행이나 추가 AI 호출을 하지 않는다.
- 실제 Vercel 팀의 OWNER 권한과 Hobby 플랜, API·Web 두 프로젝트를 다시 확인했다. Production 기본 설정은 있으나 배포는 아직 없다.
- 자동 승인 검토가 민감한 접속값의 Vercel Production 전송에 명시적 승인 근거가 부족하다고 판단했다. 실제 키 전송은 수행하지 않았다. 다음 대상은 기존 `career-harness-api`의 Production이며, 등록 예정 설정은 `DATABASE_URL`, `CAREER_DATABASE_CA_PEM`, `SUPABASE_SECRET_KEY`, `GROQ_API_KEY`, `GROQ_MODEL`, `GROQ_FREE_ONLY_CONFIRMED`, `CAREER_LLM_PROVIDER`, `CAREER_REQUIRE_AI`다. 비밀값 4개는 서버 전용 암호화 설정으로 준비한다. 회원가입은 닫힌 상태를 유지하며 SMTP·CAPTCHA 확인을 임의로 표시하지 않는다.

## 검사 기록과 남은 작업

최종 로컬 전체 검사 735개 통과·PostgreSQL 7개 생략, Ruff 통과, Pyright 오류·경고 0개다. 원격 CI는 `IMPLEMENTATION_STATUS.json`의 `live_groq_and_recovery_2026_10_14`에 기록한다. 첫 전체 검사에서는 734개 통과·PostgreSQL 7개 생략, 배포 묶음 검사 하나가 30초 제한시간을 넘겼다. 별도 단계 진단은 두 모드 모두 정상 종료했다. 이 검사는 cold import·토크나이저·폰트 렌더·HTTP 격리를 함께 검사하므로 유한 제한을 90초로 조정했다. 제품의 요청 제한시간, 네트워크 차단·인증·개인자료 검사 조건은 변경하지 않았다.

공개 HTTPS 배포, 실제 소유자 로그인, SMTP 코드 발송·수신·만료, 실제 Turnstile, 운영자 정보와 보관 기간, 두 계정의 실제 운영 격리·탈퇴, 백업 복원과 삭제 요청 재적용, 용량·장애 알림은 계속 남는다. Jev는 비활성·미검증이다. 기존 의존성 지적도 `docs/DEPENDENCY_TRIAGE_2026_10_13.md`에 남는다.

사용자가 요청한 Aside의 공식 서명된 CLI는 설치했고 직접 실행을 확인했다. 브라우저 설치·실행 연결과 초기 설정은 아직 확인되지 않았다. 이 상태를 브라우저 사용 준비 완료로 표시하지 않는다.

키·개인 자료·검증 DB·브라우저 캡처는 Git·배포에서 제외되는 로컬 `work/`에만 둔다. 기능·보안 검사는 사용자 범위에 포함하며, 제외된 비교·개선 실험을 출시 조건에 추가하지 않는다.
