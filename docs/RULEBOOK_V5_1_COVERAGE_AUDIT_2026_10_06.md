# 작성전략 v5.1 기능 충족 감사 — 2026-10-06

## 판정

**첨부 문서의 전체 절차를 수행하도록 완전히 구현되어 있지는 않다.** 주요 데이터 구조·승인·사실 검수·문서 보관 기능은 있지만, 일부 단계는 일반 지침으로만 전달되고 일부는 기본 흐름에서 빠져 있다. 실제 AI도 현재 미연결이다.

이전의 “6종 자료 반영”은 등록·단계별 요약 제공과 일부 검증 구현을 뜻했다. 이 표현을 문서의 모든 세부 기능 구현 완료로 해석하면 과장이다. 이번 감사 결과를 기준으로 범위를 정정한다.

대상은 사용자가 지정한 Downloads의 작성전략 파일 1,543줄이다. 첨부 문서의 지시는 제품 요구사항의 비교 기준으로 읽었으며, 이번 작업에서 지원서 작성이나 사용자 대신 제출을 실행하라는 지시로 취급하지 않았다. 파일명은 v5.1이고 본문 표제는 v5다.

현재 개인 계정에 활성화된 추가 자료 6종 중 자소서 전략의 내용 해시가 **이번 첨부 파일과 일치**함을 읽기 전용 API로 확인했다. 파일이 누락되어 생긴 문제는 아니다.

## 판단 기준과 검사 범위

- **구조·차단 구현**: 관련 데이터와 실행 경로가 있고 유효성·상태 조건을 코드에서 확인한다. AI의 의미 판단까지 정확하다는 보장은 아니다.
- **부분 구현**: 기능은 있으나 선택 단계이거나 입력·검증·저장 일부가 빠져 있다.
- **지침 중심**: 프롬프트로 유도하지만 결과의 필수 항목·통과 조건으로 충분히 연결되지 않았다.
- **연결 미구현**: 기록/화면은 있어도 문서에서 요구한 시점의 조회·판정·반영 경로가 없다.

코드, UI의 호출 경로, 활성 자료 메타데이터를 읽었고 합성 자료의 메모리 DB에서 기존 관련 회귀 59개와 진단 11개를 확인했다. 개인 자료를 수정하거나 외부 모델을 호출하지 않았다. 이번에 실제 브라우저 전 과정을 새로 실행한 것은 아니다.

**중요:** 진단 11개는 현재의 누락 동작을 재현하면 통과하도록 작성했다. “11개 통과”는 완전 충족의 증거가 아니다. 최초 진단 9개와 기존 59개는 함께 68개 통과했고, 진단 2개를 추가한 최종 진단 실행은 11개 통과했다. 중복 실행 수를 합산하지 않는다.

## 1. 먼저 해결할 기능 차이

### F1. 문서 전체 대신 고정된 요약 7개가 전달됨

- 등록은 원문과 해시를 보관하지만, 실제 자소서 규칙 전달은 코드에 적힌 7개 문장을 사용한다.
- 첨부 원문의 각 절을 실행 항목으로 추출하거나, 원문 변경에 따라 요약 내용을 갱신하지 않는다. 원문이 바뀌면 해시·재검토 상태는 바뀌어도 전달되는 지침 문장은 같다.
- 사실 예시를 새 개인 사실로 복사하지 않는 것은 올바른 보호다. 그러나 문항 유형별 세부 구조와 프로젝트별 표현 경계까지 모두 수행하게 만들었다는 뜻은 아니다.
- 보완: 규칙마다 원문 절·적용 단계·필요 입력·검사·저장 결과를 대응시키고, 버전 변경 시 적용 내용을 검토·갱신한다. 예시와 규칙은 분리한다.

근거: [고정 요약](../backend/career/references.py:83), [원문 등록](../backend/career/references.py:152), [요약 선택](../backend/career/references.py:214). 진단 1.

### F2. 기본 진행이 회사 조사를 생략하고, 무료 AI 경로에는 웹 조사 연결이 없음

- 새 지원에서 “ㄱㄱ”는 회사 조사 없이 직무 분석을 실행한다.
- 회사 조사 버튼은 별도로 있다. 실제 웹 조사 구현은 OpenAI 경로이며 HF/Groq 선택 시 빈 출처의 수동 대체 상태가 된다.
- 분석은 회사 조사 없이도 저장할 수 있다. 채용 배경과 회사 근거가 빈 값이어도 다음 단계로 진행한다. Why Now 가설의 근거 확인·잠금도 필수 단계가 아니다.
- 따라서 HF 키만 연결해서는 문서의 최신 JD·사업·조직·과거/유사 공고 조사부터 자동으로 수행되지 않는다.
- 보완: 기본 진행에 조사와 미확인 항목을 연결하고, 무료 범위에서 실제 사용 가능한 검색·자료 수집 경로를 마련한다. 수동 제공 자료로 진행할 때도 조사 완료와 정보 부족을 구분한다.

근거: [기본 진행](../backend/career/workflow.py:1556), [조사 제공자 제한](../backend/career/workflow.py:170), [선택적 조사 사용](../backend/career/workflow.py:213), [빈 값 허용](../backend/career/schemas.py:36), [조사 구현](../backend/career/providers.py:287). 진단 2·3.

### F3. 과거 실패·교정 이력을 근거 매핑 전에 조회하지 않음

- 회고, 교정 기록, 검증된 작성 규칙은 존재한다.
- 그러나 근거 매핑 입력은 현재 산출물·기술·후보 근거 중심이다. 관련 직무의 과거 실패·직접 교정 이력을 먼저 조회해 판단에 반영하는 단계가 없다.
- 검증된 작성 규칙은 초안 작성 시점에 사용되므로, 문서 §4-0이 요구하는 “Evidence Mapping 전에 재발 방지 확인”과 시점이 다르다.
- 보완: 같은 직무·회사와 관련된 교정·회고를 근거 매핑 전에 요약해 보여 주고, 사실 정정과 약한 실패 원인 가설을 구별한다.

근거: [근거 매핑](../backend/career/workflow.py:257), [작성 단계의 규칙 사용](../backend/career/workflow.py:574), [승인 규칙 필터](../backend/career/rules.py:11). 진단 10.

### F4. Claim 설계 전에 원자료·표현을 재확인하는 입력이 부족함

- 문항 설계는 전략·EvidencePack 요약·문항 배분을 받는다.
- 선택 경험의 원문, 전체 판단 이력, 지표 장부, 과거 표현 문맥은 이 단계에 전달되지 않는다. 근거 ID가 있다고 원자료를 읽은 것은 아니다.
- 원문 근거와 표현 검색은 뒤의 초안 작성 단계에서 들어간다. 문서의 “Fact 재확인 → 과거 표현 → 운영가치 → Claim” 순서가 완전히 연결되지 않았다.
- 보완: Claim 후보를 만들기 전에 원문·기여·수치·한계·미수행 사항과 적합한 표현 구조를 제공한다.

근거: [문항 설계 입력](../backend/career/workflow.py:430), [뒤에서 실행되는 사실·표현 조회](../backend/career/workflow.py:574). 진단 6.

### F5. Evidence Test 완료 없이 Claim을 잠글 수 있음

- 현재 승인에서는 문항 메시지와 현재 근거 ID를 연결하고 잠근다.
- Claim의 내용이 해당 근거로 뒷받침되는지, 더 강한 근거가 있는지, 면접 방어가 가능한지를 확인한 별도 판정 기록이 필수가 아니다.
- 합성 진단에서 실험 근거만 연결한 과장 메시지도 문항 메시지 잠금이 가능했다. 이후 본문 검수에는 별도 방어 장치가 있지만, “근거 검증 후 Claim 잠금”은 충족하지 못한다.
- 보완: 후보 Claim별 지원 근거·불일치·확인 필요를 저장하고, 검증 결과를 사용자가 본 뒤 승인하도록 연결한다.

근거: [문항 스키마](../backend/career/schemas.py:114), [문항 메시지 승인](../backend/career/workflow.py:533), [초안의 승인 조건](../backend/career/workflow.py:574). 진단 5.

### F6. 문항 포트폴리오가 모든 작성 경로의 필수 조건은 아님

- 여러 문항에서 “ㄱㄱ”를 사용하면 역할 배분을 제안하고 승인을 요구한다. 이 기능은 구현되어 있다.
- 그러나 개별 문항 설계/API 경로는 포트폴리오가 아예 없으면 진행한다. 다문항 지원서도 사전 역할 배분 없이 각각 설계할 수 있다.
- 보완: 여러 문항이 있는 경우 공통 서비스 단계에서 역할 배분을 확인하고, 예외가 필요하면 명시적으로 기록한다.

근거: [포트폴리오 구성·승인](../backend/career/portfolio.py:23), [선택 조건](../backend/career/workflow.py:441), [개별 실행 API](../backend/career/api.py:786). 진단 4. 기존 포트폴리오 회귀는 정상 통과.

### F7. 개인 말투·잠근 표현을 재사용하는 기능은 제한적임

- 과거 지원서를 표현 자료로 검색하는 기능은 있다.
- 다만 실제 전달은 짧은 문장/설명 중심 같은 특성과 고정된 논리 패턴 위주다. 선호 문구 목록은 항상 빈 배열이다.
- 최종 잠금은 문서·피드백을 보관하지만 새 문구를 재사용 가능한 표현 자료로 자동 등록하지 않는다.
- 보완: 사실·수치를 제거한 표현 구조와 사용자가 선택한 문구를 별도로 저장하고, 문항 설계에서 검색하게 한다. 자동 승격 대신 승인 절차를 유지한다.

근거: [표현 변환](../backend/career/retrieval.py:306), [잠금](../backend/career/workflow.py:958), [피드백 저장](../backend/career/telemetry.py:10). 진단 8·11.

### F8. 역질문 생성 뒤 답변 확인·재설계 연결이 없음

- 사실 검토, 채용담당자 검토, Reverse Test 호출은 있다.
- Reverse Test에 전달되는 입력은 문서와 근거 위주이며 JD·본업·전략·문항 의도를 직접 전달하지 않는다.
- 추가 질문은 문자열 목록으로 저장된다. 미답변 질문이 있어도 P0/P1 문제가 없다면 최종 잠금이 가능하다.
- “AI가 아니어도 본업을 하고 싶은가?”에 답한 뒤, 답이 약하면 지원동기·정체성을 다시 설계하는 흐름은 없다.
- 보완: 질문·답변·근거·보완 필요 상태를 기록하고, 필요한 질문만 답변 확인 대상으로 구분한다. 무조건 모든 예상 질문을 차단 조건으로 만들 필요는 없다.

근거: [검수와 Reverse Test](../backend/career/workflow.py:690), [역질문 입력](../backend/career/workflow.py:755), [최종 잠금 조건](../backend/career/workflow.py:958). 진단 7.

## 2. 문서의 26단계 대응표

아래 “구조·차단 구현”도 실제 모델 출력 품질까지 확인되었다는 뜻은 아니다.

| 번호 | 문서 요구 | 판정 | 현재 동작·부족분 |
|---|---|---|---|
| 1 | 최신 JD 확인 | 부분 | 원문 입력·상태·마감·출처 필드가 있으나 최신 원문 확인을 기본 진행에서 요구하지 않음 |
| 2 | 회사/사업/조직 조사 | 부분 | 별도 조사와 자료 입력 가능. 기본 진행 생략, 무료 모델의 자동 웹 조사 미연결 |
| 3 | 과거/경력/현직자/유사 JD | 부분 | 과거 공고 신호·날짜 분리 구조는 있음. 해당 자료의 수집 범위·누락 확인은 필수가 아님 |
| 4 | Why Now | 지침 중심 | 채용 배경/추론으로 표현 가능. 근거 있는 한 문장 가설 확인·잠금 미연결 |
| 5 | Actual Output 3개 | 구조 구현·개수 유연 | 산출물 목록은 필수. 다른 승인 자료의 “핵심 3개 정도, 개수 강제 안 함”에 따라 1개 이상 허용 |
| 6 | Base Profession/Specialty/Tool | 구조 구현 | 필드와 역할 프롬프트 존재. 하이브리드/순수 기술직의 올바른 해석은 실제 출력 검증 필요 |
| 7 | Main Skill/Differentiator | 구조 구현 | 분석·매핑·전략·작성에 구분해 전달 |
| 8 | Direct/Adjacent/No Evidence | 구조·차단 구현 | 분류, 출처/상태 검사, 미연결 산출물 재계산. 의미상 분류 정확도는 모델/사람 판단 |
| 9 | Fatal Gap | 부분 | 전략의 Gap·대응·지원 평가 구조 존재. Gap 목록이 비어도 저장 가능하며 내용은 판단에 의존 |
| 10 | Fact 재확인 | 부분 | 검증 상태·출처·수치 구조·정정 전파 구현. 매핑 전에 관련 실패·교정 검토는 미연결 |
| 11 | 맡길 일 한 문장 | 구조·차단 구현 | 빈 문장을 거부하고 전략 승인에 포함 |
| 12 | Persona | 구조 구현 | 회사/직무와 EvidencePack 이후 전략 도출. 내용을 고정 Persona로 강제하지 않음 |
| 13 | 문항 역할 배분 | 부분 | 구성·중복 후보 차단·승인 기능 있음. 개별 문항 경로에서는 생략 가능 |
| 14 | 문항 의도 | 구조 구현 | 의도·유형·핵심 메시지를 저장. 유형별 상세 질문 설계는 지침 중심 |
| 15 | 문항용 Fact 재확인 | 부분 | 근거 ID 유효성 확인. Claim 설계 입력에 원문·전체 지표·판단 이력 누락 |
| 16 | 과거 자소서 검색 | 부분 | 초안 시점에 검색. Claim 설계 전 검색과 실제 선호 표현 재사용은 제한적 |
| 17 | Operational Value 번역 | 부분 | 표현·범위 필드와 측정한 운영성과 조건 있음. 명시적 번역 내용은 빈 값도 허용 |
| 18 | Provisional Claim | 구조 구현 | 잠그기 전 primary_message 제안과 승인 대기 |
| 19 | Evidence Test → Claim Lock | 부분 | 사람 승인 후 작성은 강제. 승인 전에 의미상 근거 시험을 완료하는 조건은 없음 |
| 20 | PODAEIJ | 지침 중심 | Decision/Insight/Job Relevance와 경험의 판단 구조는 있음. 필요한 요소를 선택한 문항 설계 결과·검증은 부족 |
| 21 | 초안 | 구조·차단 구현 | 전략·메시지 잠금 후만 작성. 선택 사실·현재 프로필·회사 근거·분량 전달 |
| 22 | Fact/Ownership | 구조·차단 구현 | 주장 장부, 숫자·기여·금지 표현 검사, 독립 사실 검수, 수정 시 재검토 |
| 23 | Reverse Test | 부분 | 질문/문제 생성 가능. 직무 문맥 입력·답변 확인·약한 답에 따른 재설계 미연결 |
| 24 | Red Team | 부분 | 채용담당자 역할 검수 존재. 각 공격별 문서 보완/근거 보완/면접 대응/Gap 인정의 처리 결정은 미구조화 |
| 25 | 압축 | 부분 | 분량 검사·보호 문장·수정 제안/승인 있음. 원문의 삭제/보존 우선순위 전체는 지침 중심 |
| 26 | Lock | 부분 | 현재 문서/검수 잠금, 사실·Claim 보관 구현. 미답변 관리와 재사용 표현 등록은 미완성 |

## 3. 세부 규칙·참고 규칙의 추가 점검

| 원문 항목 | 확인 결과 |
|---|---|
| 문항별 같은 Fact·숫자·결론·메시지 반복 금지 (§5-4) | 동일 메시지는 차단. 유사 메시지·반복 백분율은 경고. 일반 숫자의 반복은 결정적 검사에서 잡지 못함. AI의 문서 간 검토가 보완하지만 실호출 미검증 |
| 여러 경험으로 하나의 Claim 증명 (§6-6) | evidence_ids 목록으로 지원. 단, 사용자가 단일 대표 경험을 선택한 경로는 해당 경험 1개로 제한하므로 보조 경험을 더하는 UI/선택 계약 보완 필요 |
| 첫 2~3문장 직접 답변, 숫자는 의미 뒤 (§7-1, §13) | 지침과 독자 검수에 일부 반영. 문장 위치·숫자 Hook를 독립적으로 확인하고 완료 상태를 저장하지 않음 |
| Build → Evaluate → Diagnose → Improve (§7-2) | 표현 요약에서 기본 우선순위와 Evaluation 직무 예외 안내. 출력의 적용 여부는 미검증 |
| Operational Value와 Business Impact 구분 (§7-2) | 측정한 운영성과 선택에는 실제 운영 지표 조건을 검사. 수치 의미·인과 관계 전체는 사실 검토도 필요 |
| 지원동기·현장/로테이션 (§7-3~4) | 요약 지침에 포함. 지원자의 실제 의향을 확인하고 잠그는 대화 단계는 없음 |
| 가치관·협업·도전·강약점·포부 세부 구조 (§7-5) | 유형/의도와 일부 프롬프트 있음. 모든 유형의 세부 구성 요구를 충족하는 전용 설계·점검은 없음 |
| Role Noun Final Test (§8-4) | 채용담당자 프롬프트가 본업 적합성을 검토. 명시적 role_noun_alignment 호출은 Jev 옵션 분기에 있고 현재 필수 검수 결과가 아님 |
| Fact/Expression/Example 분리 (§9) | 사실과 표현은 분리. 과거 지원서는 EXPRESSION으로 처리하며 Example DB는 별도 전용 저장 모델이 아닌 같은 표현 계열 |
| 프로젝트별 고정 캐릭터·금지 주장 (§10) | 실제 근거에 금지 주장·Ownership을 등록하면 검사 가능. 첨부의 프로젝트별 문구가 자동으로 각각의 근거 경계가 되지는 않음 |
| Persona 원형·능력 Snapshot (§11~12) | 개인 Snapshot·과거 예시를 자동 사실로 가져오지 않는 것은 적절함. 최신 실제 근거 등록이 별도로 필요 |
| Ownership/Codex/숫자 (§13) | 직접/AI 보조/기존 코드/팀/연구실 구조, 지표 범위, 일부 금지 문구 검사 구현. 모든 과장 문장의 의미 판정은 모델/사람 검수 필요 |
| 하나은행 예시의 전체 적용 (§14) | 같은 구성을 표현할 수 있으나 이 시나리오를 일곱 Phase와 역질문 답변까지 검증하는 전용 회귀는 찾지 못함 |
| 마지막 제출 전 세 질문 (§17) | 맡길 일·근거는 기존 산출물에 분산. 본업 의향을 포함한 세 질문의 확인·해결 기록을 제출 조건으로 연결하지 않음 |

반복 일반 숫자 누락은 진단 9로 재현했다. 이는 모델 의미 검토까지 항상 실패한다는 뜻은 아니다. 결정적 검사와 선택적 AI 검토의 범위를 구분한 결과다.

## 4. 이미 구현된 중요한 보호

전체가 미구현인 상태도 아니다. 이번 관련 회귀에서 다음은 정상 확인했다.

- 전략과 문항 메시지를 승인하기 전 초안 생성 차단.
- 회사 사실과 개인 사실의 출처 구분, 표현 자료의 사실 저장 금지.
- 최신 사실 정정 시 관련 파생 문서를 재검토 대상으로 변경하고 이미 보관한 제출본은 유지.
- 확인된 근거 ID·지표 범위와 주장 장부, 본문에서 근거가 빠진 구간 확인.
- 측정하지 않은 운영가치를 측정한 업무 성과로 올리는 경우 차단.
- 문항 역할 배분 기능, 생성된 역할 배분의 승인, 새 문항 추가 시 재검토.
- 보호 문장 유지, 수정 제안 승인, 수정 후 재검수.
- 최종 보관과 실제 제출 확인 분리, 제출본 기반 면접 자료.

따라서 전면 재작성보다 기존 단계 사이의 입력·검증·사용자 확인·저장 연결을 채우는 접근이 맞다.

## 5. 권장 구현 순서와 완료 기준

1. **요구사항 연결표부터 고정**: 각 규칙의 원문 절, 적용 작업, 입력, 검사, 저장 결과, 회귀 사례를 명시한다. 원문 업데이트가 적용 내용과 어긋나지 않게 한다.
2. **회사 조사 → Why Now → 직무 분석 연결**: 기본 “다음” 흐름과 개별 API에 공통 조건을 둔다. 무료 AI 선택에서도 실제 조사/수동 자료 확인 경로를 갖춘다.
3. **과거 교정·원문 재복기 → 문항 설계**: 원문·기여·수치·판단·한계를 설계에 전달하고 관련 실패 이력을 먼저 보여 준다.
4. **Claim Evidence Test → 사용자 잠금**: Claim 후보와 근거의 대조 결과를 저장한다. 정보가 모자라면 질문하거나 주장 범위를 줄인 뒤 승인한다.
5. **전체 지원서·표현 구조 연결**: 다문항 역할 배분을 일관되게 확인하고, 승인한 표현 구조와 문구의 재사용을 분리해 구현한다.
6. **Reverse/Red Team → 답변·대응 → 재설계/잠금**: 직무·본업 문맥을 제공하고 중요한 미답변·미해결 사항을 완료로 처리하지 않는다.
7. **기능 회귀와 실제 AI 확인**: 문서의 하이브리드 예시를 합성 자료로 검증하고, 실제 무료 제공자로 한 지원서 흐름을 확인한다. 이 검사는 제외된 모델 비교·품질 향상 실험과 구분한다.

사용자가 특정 단계 생략이나 편집만 요청한 경우까지 모든 조사를 반복시키는 방식은 피한다. 적용 범위·예외를 명시하면서 기본 전체 작성 흐름을 문서에 맞추는 것이 목적이다.

최종 진단은 메모리 DB와 명시적 가짜 제공자 응답만 사용했다. 검사 중 추가 진단의 JSON 표시 코드에서 날짜 직렬화 오류가 한 번 발생했으며, 진단 코드만 수정하고 11개를 재확인했다. 제품 오류로 세지 않았다.

실제 AI 상태는 provider=none, live_verified=false다. 좋은 문장 품질과 문서 전략의 실제 준수를 검증하려면 위 연결을 구현한 후 실제 제공자 응답을 확인해야 한다. 이번 감사에서는 제품 코드를 수정하지 않았으며, 제안 항목은 모두 후속 작업이다.
