# 공개 가입형 배포

기존 초대형과 같은 코드로 공개 가입형을 선택한다. `CAREER_ACCESS_MODE=invite`가 기본값이며, `public`에서는 이메일을 인증한 사람이 초대 없이 가입한다. 공개 회원 수를 소수로 고정하는 제한은 없다. 무료 DB·AI·호스팅 용량이나 동시 사용자 수를 보장한다는 뜻은 아니다.

## 1. 환경 선택

기존 `deploy/backend.env.example` 또는 `deploy/vercel-backend.env.example`를 먼저 적용하고 `deploy/public-access.env.example`의 공개 설정을 추가한다. 실제 비밀값은 서버의 환경 설정에만 넣는다. 공개/초대 환경을 동시에 운영하면 각각 다른 Supabase 프로젝트·DB·키를 사용하는 것이 좋다. 이 작업에서는 현재 로컬 개인 환경을 공개 모드로 전환하지 않았다.

공개 production/staging은 다음 정보가 없으면 시작을 거부한다.

- 실제 운영자 이름, 문의 이메일, 백업 보관 일수
- Supabase 인증 설정과 브라우저용 publishable/anon 키
- 계정 삭제에 사용하는 서버 전용 secret/service_role 키
- Turnstile site key와 CAPTCHA·SMTP·이메일 확인 설정에 대한 운영자 확인 표시

확인 표시는 원격 설정을 자동 검사한 결과가 아니다. 빈 정보를 임의로 채우거나 실제 점검 없이 `*_CONFIRMED=1`로 바꾸지 않는다.

## 2. Supabase 가입·메일·봇 차단

1. 새 사용자 가입을 허용하고 이메일 확인을 켠다. 익명 로그인을 끈다. 앱은 서명된 JWT의 비익명 계정 여부와 최초 가입 시 Auth `/user`의 확인된 이메일을 검사한다. 사용자 메타데이터의 자기 신고값으로 인증하지 않는다.
2. 사용자에게 메일을 보낼 실제 SMTP를 연결한다. Supabase 기본 발송기는 운영 서비스 용도가 아니며 발송 가능한 수신자와 한도가 제한된다.
3. 이메일 템플릿에 **`{{ .Token }}`** 코드를 포함한다. 이 UI는 인증 코드를 입력하는 방식이다. 링크만 있는 기본 템플릿으로는 완료할 수 없다. OTP 길이는 6~8자리, 만료 시간은 서비스 정책에 맞게 설정한다. 앱은 재발송 버튼을 60초 동안 제한한다.
4. Cloudflare Turnstile에서 실제 프런트 도메인을 허용하고, Supabase Auth에 맞는 secret을 등록해 CAPTCHA를 활성화한다. 앱에는 공개 site key만 제공한다. 브라우저 버튼 차단만으로 봇 방지가 된다고 판단하지 않는다.
5. 별도 테스트 이메일로 코드 발송·오류·만료·재발송과 봇 검증을 실제 도메인에서 확인한다. 타인의 주소로 테스트 메일을 보내지 않는다.
6. 계정 삭제에 필요한 backend secret은 브라우저·공개 설정 응답에 들어가지 않는다. 권한을 가진 별도 테스트 계정을 만들어 내보내기→새 이메일 OTP→삭제를 확인한다.

공식 안내: [이메일 OTP](https://supabase.com/docs/guides/auth/auth-email-passwordless), [CAPTCHA](https://supabase.com/docs/guides/auth/auth-captcha), [메일 발송](https://supabase.com/docs/guides/auth/auth-smtp), [인증 요청 제한](https://supabase.com/docs/guides/auth/rate-limits), [서버에서 사용자 삭제](https://supabase.com/docs/reference/javascript/auth-admin-deleteuser).

## 3. 자료·사용량 보호

신규 계정의 기본 AI 상한은 하루 10회·월 100회 및 하루 50,000·월 300,000토큰이다. 이는 제공자 호출 수이며 대화나 문서 한 번과 같지 않다. 한 작업에서 여러 호출이 생길 수 있다. 운영자는 계정별 상한과 전체 공용 상한을 관리한다. 새 기본값은 이미 가입한 계정의 정책을 덮어쓰지 않는다.

인증된 계정별 DB 요청 제한은 기본 분당 120회, 변경 요청 20회다. 여러 서버에서도 동일 UUID의 원자적 장부를 사용한다. 비인증 공격·다계정 남용·외부 인증 메일 남용은 호스팅의 입구 제한과 Supabase 설정으로 함께 관리한다. 무료 계정만으로 공개 트래픽을 무제한 수용할 수는 없다.

계정별 지원 100개·근거 500개·원자료 500개·아티팩트 5,000개 상한과 기존 업로드 개인/전체 용량 상한을 적용한다. 삭제·무효화된 이력도 보관 개수에 포함될 수 있으므로 사용자가 한도를 올려 우회하지 못하게 한다. 이 개수 제한은 DB 전체 용량 보증이 아니다. 대화/운영 이력과 백업을 포함한 실제 저장량을 관찰해야 한다.

운영자는 계정 ID로 검색하고 50개씩 조회한다. 계정 중지는 기존 로그인에도 적용한다. 개인정보 문서 내용은 이 회원 관리 목록에 노출하지 않는다. 새로운 DB 테이블도 migration 0013과 `deploy/supabase-security.sql`에서 Data API 접근을 차단한다.

## 4. 동의·내보내기·탈퇴

가입 후 현재 약관·처리 안내 버전에 동의하기 전에는 작업실 기능을 차단한다. 안내가 바뀌면 `CAREER_POLICY_VERSION`을 올린다. 거절한 사람도 계정 관리와 자기 자료 내보내기·삭제를 사용할 수 있다. 모든 계정 관리 요청은 인증이 필요하다.

탈퇴는 같은 계정의 최근 5분 내 OTP 인증 증거와 `DELETE` 확인을 요구한다. 새로 갱신한 JWT만으로는 최근 본인 확인으로 간주하지 않는다. 접근 중지 기록을 먼저 저장하고 취업 자료·검색 벡터를 제거한 다음 Supabase Auth 계정을 삭제한다. 진행 중 작업은 최종 저장 때 계정 상태를 다시 검사한다. 외부 Auth 삭제가 실패하면 접근 차단을 유지하며 재시도 상태를 표시한다.

사용량 장부, 최소 접근 차단 기록과 삭제 처리 기록은 보존한다. 기존 백업은 자동 삭제하지 않는다. 운영자가 실제 백업 만료·복원 시 삭제 요청 재적용 절차를 정해야 한다. `/privacy`와 `/terms`는 구현 동작을 설명하는 기본 문안이다. 공개 전에 실제 운영 주체, 호스팅/AI 처리자와 지역·보관 조건에 맞게 검토하고 완성해야 한다. 법률 적합성 인증을 받은 문안이 아니다.

## 5. 배포 및 운영 인수

기존 `docs/VERCEL_FREE_BACKEND.md`, `docs/PRODUCTION_DEPLOYMENT.md`의 인증서 검증·분리 마이그레이션·환경별 설정을 따른다. 배포 중 서버리스 시작 시 DB를 변경하지 않는다. 배포 전 `alembic upgrade head`와 `alembic check`를 운영자가 지정한 DB에 실행하고 보안 SQL을 확인한다.

`scripts/deployment_preflight.py`는 기본적으로 설정을 검사한다. `--check-database`와 `--check-public-keys`는 명시적 읽기 검사를 추가한다. 설정 통과가 SMTP·CAPTCHA·AI 문서 응답·HTTPS 검사를 대체하지 않는다. AI는 운영자의 무료 계정·키와 실제 한도를 확인한 후 연결한다. 유료 전환·비교 실험·Jev shadow 호출은 자동으로 켜지지 않는다.

공개 전 확인할 항목:

- 실제 두 테스트 계정 사이의 자료 격리, 인증 만료, 중지된 계정 거부
- 실제 메일 코드와 CAPTCHA, 재가입·동의 버전 변경·탈퇴 재시도
- 실제 AI 문서 응답과 호출/토큰 장부, 제공자 무료 한도
- 백업 복구, 삭제 요청 재적용, DB/AI 한도와 오류 알림
- 배포된 HTTPS 도메인의 보안 헤더·정책 링크·모바일 화면
- 공개할 소스의 개인정보 검사, 원격 CI, 무료 호스팅 플랜의 실제 사용 조건

가입을 중단하려면 `CAREER_REGISTRATION_OPEN=0`으로 앱의 새 회원 승인을 막는다. 기존 가입자의 로그인은 유지한다. Auth 계정 생성 자체까지 막으려면 Supabase에서도 신규 가입을 끈다. 긴급 AI 중지는 운영 화면에서 공용 호출 상한을 0으로 설정한다. 이미 시작된 요청은 취소되지 않으며 보수적으로 사용량을 정산한다.
